# إصلاحات الفحص الأمني الشامل

هذا سجل الإصلاحات المطبَّقة بعد الفحص الأمني الشامل للمنصّة. لكل نتيجة الرقم
المرجعي نفسه المستخدم في تقرير الفحص الأصلي (F-01 إلى F-05).

## ما تم إصلاحه

| المعرّف | الوصف | الخطورة | الحالة |
|---|---|---|---|
| F-01 | لا يوجد تحقق من نطاق قيمة التقييم (Ratings) | متوسطة | ✅ أُصلح — ثم لاغٍ (أُزيلت ميزة التقييم) |
| F-02 | فشل صامت في تحديث عدّاد بلاغات الإعلان | منخفضة–متوسطة | ✅ أُصلح |
| F-03 | إمكانية تلفيق التقييم عند إنشاء الحساب مباشرة | منخفضة | ✅ أُصلح — ثم لاغٍ (حقل `rating` أُزيل من الملف) |
| F-04 | غياب التحقق من صحة السعر والقسم عند إنشاء الإعلان | منخفضة | ✅ أُصلح |
| F-05 | غياب رؤوس أمان HTTP | منخفضة | ✅ أُصلح جزئيًا (راجع الملاحظة) |
| F-06 | عدّاد المشاهدات قابل للتضخيم دون حد | معلوماتي | ⏳ مؤجَّل (مخاطرة منخفضة القيمة، قرار مقبول) |
| F-07 | تسريب "هل الرقم مسجّل" عبر استعادة كلمة المرور | معلوماتي | ✅ أُصلح |

## تفاصيل الإصلاحات

### F-01 — نطاق قيمة التقييم (`firestore.rules`, مجموعة `ratings`)
أُضيف الشرط `request.resource.data.value is int && value >= 1 && value <= 5`
لقاعدتَي `create` و`update`. **تحقق حيّ:** قيمتا `999999` و`-500` كانتا
تُقبلان قبل الإصلاح، أصبحتا تُرفضان بعده؛ القيم الصحيحة `1` و`5` بقيت تُقبل
بلا مشاكل.

### F-02 — عدّاد بلاغات الإعلان (`firestore.rules`, مجموعة `ads`)
أُضيف استثناء لقاعدة تحديث `ads` يسمح لأي مستخدم مسجّل دخول بزيادة
`reportsCount` بمقدار +1 بالضبط ولا شيء غيره (بنفس أسلوب استثناء `views`
الموجود أصلًا). **تحقق حيّ:** قبل الإصلاح، تقديم بلاغ كمستخدم ليس بائع
الإعلان كان يُنشئ مستند البلاغ بنجاح لكن يفشل في زيادة العدّاد (رسالة خطأ
كاذبة للمستخدم + عدّاد يبقى صفرًا دائمًا في لوحة الإدارة). بعد الإصلاح: كلا
الجزأين ينجحان، والقفزات في العدّاد (`+10` بدل `+1`) أو تجميع تغييرات حقول
أخرى مع التحديث ما زالت مرفوضة.

### F-03 — تلفيق التقييم عند إنشاء الحساب (`firestore.rules`, مجموعة `users`)
أُضيف الشرط `rating == 0 && reportsCount == 0 && adsCount == 0` لقاعدة
الإنشاء. **تحقق حيّ:** محاولة إنشاء ملف مستخدم بـ `rating: 5` مباشرة عبر
Firestore API أصبحت تُرفض؛ الإنشاء الطبيعي (عبر `createUserProfile()`، بقيم
تبدأ من صفر) بقي يعمل بلا تغيير.

### F-04 — التحقق من السعر والقسم (`firestore.rules`, مجموعة `ads`)
أُضيف الشرط `price >= 0 && category in ["livestock","feed","equipment","services","transport"]`
لقاعدة الإنشاء (استُثني `offers` عمدًا — قسم متوقف لم يعد متاحًا لإعلانات
جديدة؛ الإعلانات القديمة بهذا القسم غير متأثرة لأن القيد على الإنشاء فقط،
لا التعديل). **تحقق حيّ:** إعلان بسعر `-99999` وقسم وهمي أصبح يُرفض؛ إعلان
عادي بسعر `500`، **وإعلان بسعر `0`** (يعني "السعر عند الاتصال" في الواجهة —
حالة حرجة تحققت منها عمدًا) بقيا يعملان بلا مشاكل.

### F-05 — رؤوس أمان HTTP (`firebase.json`, `public/_headers`)
أُضيفت الرؤوس التالية على كل من Firebase Hosting وCloudflare Pages:
`X-Frame-Options: DENY`، `X-Content-Type-Options: nosniff`،
`Referrer-Policy: strict-origin-when-cross-origin`، مع
`Strict-Transport-Security` على Cloudflare تحديدًا (موجودة أصلًا تلقائيًا
على Firebase Hosting). **تحقق حيّ:** الرؤوس الأربعة مؤكَّدة على كلا
الموقعين، على صفحات HTML والملفات الثابتة معًا، والموقع يعمل بشكل طبيعي
بعد التغيير (لا أخطاء جديدة في الكونسول، تصفح الإعلانات يعمل).

**ملاحظة مهمة — لماذا لم تُضَف `Content-Security-Policy`:** المنصّة تتصل
بعدة نطاقات Google/Firebase (Firestore، Identity Toolkit، Cloud Functions،
reCAPTCHA الخاص بالتحقق عبر الجوال) — بناء قائمة CSP دقيقة لكل هذه النطاقات
يحتاج اختبارًا مخصصًا وموسّعًا (خصوصًا لمسار "نسيت كلمة المرور" الذي لم
يُنشر بعد أصلًا)، وأي خطأ في القائمة قد يُعطّل تسجيل الدخول أو التحقق بصمت.
تفاديًا لخرق الالتزام بعدم كسر أي وظيفة، تُرك هذا كتوصية منفصلة تحتاج تصميمًا
واختبارًا مرحليًا مخصصًا (راجع تقرير الفحص الأصلي).

### F-07 — تسريب "هل الرقم مسجّل" (`functions/src/index.ts`)
كانت `startPhoneReset` ترمي `not-found` عندما يكون الرقم غير مسجّل، ما يجعلها
أداة تعداد أرقام (phone enumeration oracle). الآن:
- عند رقم غير معروف تُرجع الدالة استجابة بنفس الشكل الطبيعي مع `resetId`
  عشوائي مبهم لا يمكن لأي خطوة لاحقة التعامل معه (ولا يُنشأ أي مستند
  `password_resets`).
- `completePhoneReset` توحّد جميع حالات الفشل (مُعرّف غير صالح/مستهلك/منتهي/
  رقم غير مطابق) في رسالة واحدة عامة `"تعذّر التحقق، يرجى طلب رمز جديد"`.
- نص صفحة "نسيت كلمة المرور" أصبح: «إن كان الرقم مسجّلاً لدينا فستصلك رسالة».

**المقايضة:** يواصل العميل استدعاء رسالة Firebase Phone Auth لأي رقم صحيح،
فقد تصل رسالة نصية لرقم غير مسجّل خاض التدفق — لكن المهاجم لم يعد يميّز
النجاح من الفشل، وحدود إساءة الاستخدام و reCAPTCHA من Firebase سارية.

## الحالة الأمنية بعد الإصلاح

جميع نتائج فئة "سلامة البيانات" (F-01 إلى F-04) — وهي كل الثغرات ذات
الخطورة المتوسطة والمنخفضة الفعلية المكتشفة في الفحص — **مُصلحة ومُتحقَّق
منها حيًا**. الفجوة الوحيدة المتبقية من فئة "التحصين" (CSP الكاملة) قرار
مؤجَّل بوعي وليس إغفالًا. لا تغيّر أي إصلاح من هذه سلوك أو وظيفة ظاهرة
للمستخدم — كلها تشديد لقواعد كانت تسمح بأكثر مما ينبغي.
